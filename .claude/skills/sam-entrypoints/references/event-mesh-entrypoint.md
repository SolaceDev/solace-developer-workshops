# Event-mesh entrypoint (GA)

Turns Solace broker messages into agent or workflow tasks, and optionally publishes the results back to the mesh. This is the **trigger half** of "listen → filter → store": the entrypoint fires the task; branching/filtering logic and multi-step processing belong in a workflow (`sam-author-agent`), which an event rule can target directly. The reverse direction — an *agent* sending requests onto the mesh as a tool — is the `event_mesh` **connector** (`sam-connectors`).

Field names below are real keys for recognition; full YAML belongs to `sam-declarative-config` (or pull a UI-created entrypoint). In the builder UI, event rules have a dedicated editor, not a generic form.

## Broker connection

Point the entrypoint at the event-source broker with explicit details: `broker_url` (`tcp/tcps/ws/wss`), `broker_vpn`, `broker_username`, `broker_password`, `tls_skip_verify` (leave `false` outside dev). Leaving `broker_url` empty falls back to the local dev broker only when no broker URL resolves at all (the runtime keys off that, not off an "is this embedded/desktop" check). A deployed entrypoint still needs real broker details: whenever the platform has a system broker configured, create **and** update reject a blank `broker_url`/`broker_vpn`/`broker_username`/`broker_password` with a 422 — the same path `sam config apply` takes.

## Event rules (the heart of the type — at least one)

Each rule says *what arrives*, *who handles it*, and *what goes back out*:

- **Match:** `name` (unique), `subscriptions` — one or more topics, Solace wildcards `*` and `>` supported, per-subscription `qos` (default 1). `messageFormat` declares the payload encoding: `json` (default), `text`, `xml`, `raw_bytes`, `protobuf`, `structured`.
- **Target:** `targetAgent` **or** `targetWorkflowName` — mutually exclusive (setting both is rejected); if neither is set the rule defaults to an agent target (the built-in Orchestrator). An agent target (including the Orchestrator default) takes `promptTemplate`, the template that turns the message into the task input — it can expand the whole `{payload}`, the `{topic}`, or JSON fields like `{payload.order.id}`. A workflow target ignores `promptTemplate` and takes `inputExpression` instead — set it on every workflow rule, or the workflow receives empty input; `"input.payload:"` delivers the payload as the workflow's text input (`workflow.input.text`) — a payload that parses as JSON is re-serialized as JSON text (not as addressable fields), any other payload passes through as-is. `structuredInvocation` attaches input/output JSON Schemas to an agent target (the agent validates and retries); a workflow target ignores it and applies its own schemas.
- **Identity:** `defaultUserIdentity` (static, e.g. `order_event_user`) or `userIdentityExpression` (per-message). This is what RBAC and audit attribute the task to — don't leave it implicit for production rules.
- **Acknowledgment:** `acknowledgmentPolicy.mode` = `on_receive` (default — ack when the message arrives) or `on_completion` (ack only after the task finishes; `timeoutSeconds` default 300). A task whose result is published is acked — including a failed workflow run whose failure is published, which is never nacked, so a deterministic failure is not redelivered forever. `onFailure` applies only when the task returns a JSON-RPC error, the result fails to publish, the timeout fires, or the event can't be turned into a task (a target or input expression fails, its identity is rejected, the caller lacks permission to invoke the target, or submission otherwise fails); its `nackOutcome` (`rejected`/`failed`) is *intended* to select drop vs redeliver, though the runtime currently nacks the message the same way for both. Choose `on_completion` when losing a message on task failure is unacceptable.
- **Outputs:** `successOutput` and `errorOutput`, each with `enabled`, `topic` (`topicType` `static`, or `dynamic` for an expression-built topic), and `responseType` (`text` final text — the success default, `full` entire response, `structured` — the response's `structured_output`: an agent target's schema-validated result when the rule sets `structuredInvocation` (the success default for such a rule; only `structured` carries the validated object, `text` is empty and `full` holds just a reference to it), or a workflow target's result; `error` — the error-output default; or `custom`). An output publishes **only when `enabled: true`**; without it the block is ignored and nothing is published. A `dynamic` topic expands `{{text://…}}` blocks evaluated against the task's response: `input.payload:<field>` reads the response (`text`, `structured_output`, …), and `user_data.forward_context:<key>` reads a value the rule's `forwardContext` captured from the inbound message — the only way to put an inbound field into the reply topic. A single-brace placeholder such as `orders/processed/{id}` is published literally. For a workflow target, publish its result with `responseType: structured` (or `custom` with `customExpression: input.payload:data[0]`), and give `errorOutput` its own `responseType` (`text` or `error`). `errorOutput` receives, for any target, an error response (the agent or workflow returned an error instead of a result — for example the agent's `required_scopes` are not met, the model call fails, or the target stops responding and the task times out; the acknowledgment `timeoutSeconds` only settles the message — the task keeps running and its result is still published) and a `userIdentityExpression` that resolves to nothing while the rule sets no `defaultUserIdentity`; and a failed, rejected or canceled run of a workflow target or of a structured invocation. An agent target without `structuredInvocation` publishes every final result on `successOutput`, even a run marked failed after a tool failure the agent recovered from. An event the entrypoint can't turn into a task (a target or input expression fails, the caller lacks permission to invoke the target, or submission otherwise fails) is not published on either output — except that unresolved `userIdentityExpression`, which goes to `errorOutput`. If the user wants the result somewhere other than a topic (a DB), that's a connector on the agent/workflow side, not an entrypoint output.

## Worked shape (in words, not YAML)

"When an order event lands on `orders/new/>`, process it with the order-triage agent, publish the result to `orders/processed`" = one rule: subscription `orders/new/>` (json) → `targetAgent: order-triage` with a promptTemplate embedding `{payload}` → `successOutput` with `enabled: true` and topic `orders/processed`, plus an enabled `errorOutput` topic so errors are visible on the mesh. Decide `on_receive` vs `on_completion` from whether a dropped event matters.

## Verify

Publish a test message to a matching topic (broker Try-Me tab or any client) and watch (a) the task appear in the web UI, and (b) the success topic. Rule cross-field mistakes (an agent target without promptTemplate, both targets set) are rejected at save time with the reason. A workflow rule without `inputExpression` is not rejected — it saves, deploys, and hands the workflow empty input, so check it before applying.
