# MCP entrypoint (early access)

Exposes Agent Mesh agents as MCP tools to external MCP clients (Claude Code, Cursor, MCP Inspector, custom clients). **Direction check:** consuming a remote MCP server across agents = `mcp` connector (`sam-connectors`); inline on one agent = `sam-author-agent`. This page is your-agents-as-the-server.

## How agents appear to clients

**One MCP tool per agent skill**, named `<prefix>_<skill_name>` (sanitized to lowercase alphanumeric + underscores) — not one opaque "ask the agent" tool. **The prefix comes from the agent's card name, never its display name.** A platform-deployed component's card name is `<kind>_<underscored-uuid>` (`agent_019e9445_4061_7104_87a5_3e29ad2fe230`, 42 characters — the UUID's dashes become underscores), which leaves too little of the 64-character provider ceiling for the skill name, so the prefix keeps only the UUID's **last** 8 hex digits: `agent_ad2fe230`, `workflow_1c2d3e4f`. The tail rather than the head because these are UUIDv7 — the leading digits are the mint timestamp at roughly 65-second granularity, so ids minted in one batch are identical over their first 8. A card published under a plain name (a built-in such as `Builder`, or a YAML agent) is already short and broker-safe and is kept whole. **Tool names are therefore stable across a rename**: a filter pattern, or a consuming connector's manifest, written against a tool name survives an agent being renamed. A name still over 64 characters is truncated, with a digest of the full name appended so two names that agree on the surviving head stay distinct — the digest is a tie-breaker, not the uniqueness guarantee; that comes from the ownership check next. When a composed name is already owned by a *different* agent — which takes two components of the same kind whose ids end in the same 8 hex digits, so it is rare rather than routine — that agent's tool falls back to its **full** card name — 43 characters before the skill name, so any skill name over 21 characters pushes the fallback into truncation — and if that name is taken too the tool is omitted from the catalog entirely; which of the contenders keeps the preferred name is decided by discovery order. For a plain-named card the fallback composes the identical string and so cannot rescue it — that is the routine route to omission. Two skills on *one* card that compose to the same name keep only the first; the second is dropped. All of these outcomes are logged with the tool names involved, as is any truncation. The catalog updates live as agents come and go.

Each half of the name must contribute at least one ASCII letter or digit, since sanitizing replaces everything else with underscores. The test is applied after case folding, so the handful of non-ASCII runes that fold to ASCII — `K` (U+212A) folds to `k`, `İ` (U+0130) to `i` — do count, and match what sanitizing then emits. **When a skill's name contributes none — one named only in a non-Latin script, or one with no `name:` at all, which the agent-card parser neither defaults nor rejects — the skill's ID is used for that half instead**, so an agent's non-English skills stay distinct rather than all collapsing onto the bare prefix. If neither the skill's name nor its ID can contribute, or the prefix can't, the tool is omitted rather than named after whichever half survived; both outcomes are logged with the skill names involved.

**The agent's display name rides in the tool's description and its MCP title annotation**, not in its name: the description opens with `Agent: <display name>` before the skill's own text, and the title a client renders in place of the id-derived name is `<display name>: <skill name>`. That is the only thing telling a model two agents' same-named skills apart, so an agent author's display name and skill descriptions are what make a crowded catalog usable; a card carrying no display-name extension falls back to its card name in both places. The label is read when the card is registered, so it refreshes only once the agent is redeployed and rediscovered and can read stale until then — a cosmetic label, not a routing or filter break.

`includeTools` / `excludeTools` patterns (exact or regex, matched against the agent's **card** name — `agent_<underscored-uuid>` for platform-deployed agents (the UUID's dashes become underscores), never the display name — the skill name, or the final tool name) narrow what's exposed. Resolution is specificity-ordered — an exact match beats a regex, so an exact `includeTools` entry overrides a regex `excludeTools`; between equal specificities, exclude wins. **A pattern written against the final tool name must match the composed name exactly**: the shortened `<kind>_<uuid-tail>` prefix rather than the full card name the card-name axis matches, and a truncated name in its truncated form. A pattern on the card name or the skill name does not depend on the composed name. **A non-empty `includeTools` flips the default from accept to reject**, so it exposes only what its patterns match and an allowlist matching nothing exposes nothing, with no error. (The other way to an empty catalog is an RBAC principal holding no invoke scopes — check both.) A non-matching `excludeTools` entry is inert.

Both fields are arrays of **objects**, each carrying a single `pattern` string (1–255 characters) — the served schema reports the type as `array<object>` but does not describe the object, so a bare string passes `plan` and fails `apply` with `422 includeTools[0]: must be an object`:

```yaml
values:
  includeTools:
    - pattern: weather_agent
    - pattern: "^billing_.*"
  excludeTools:
    - pattern: billing_refund
```

## Connecting a client

The endpoint is `<external-base>/gw/<slug>` (the entrypoint proxy; MCP mounts at the entrypoint root — the `/gw/<slug>` slug already addresses it, so there is no endpoint sub-path). **Set the slug when you create the entrypoint** — it is opt-in and *not* derived from the name, so if you skip it the endpoint is `/gw/<uuid>` (an opaque UUID clients must hardcode) instead of a readable path. The slug is immutable after creation, so choose it up front. Locally, `<external-base>` is the WebUI's origin; for deployments, read it from the entrypoint's **networking details** view in the UI rather than guessing. Transport is **Streamable HTTP** (the config value is historically spelled `sse`/`http` — same thing). For Claude Code:

```
claude mcp add --transport http sam <external-base>/gw/<slug>
```

then `/mcp` inside Claude Code to check status and complete login when auth is on. `corsAllowedOrigins` left empty allows every origin, so browser-based clients (MCP Inspector, MCPJam) work out of the box; once you set it, list each browser client's Origin, since any other origin is then refused.

## The four auth modes (say which one you're setting up)

`enableAuth` selects **authentication**; the authorization service selects **authorization**. They are independent — turning `enableAuth` off does *not* opt the entrypoint out of RBAC — so pick a row by both columns, not by one "auth on/off" axis.

| Mode | Config | tools/list | tools/call |
|---|---|---|---|
| No auth (dev/trial) | `enableAuth: false`, no authorization service | unfiltered | every caller acts as the entrypoint's unauthenticated identity, nothing gated |
| Authorization only | `enableAuth: false` **+ an authorization service** | **filtered** to the unauthenticated principal's scopes — **empty** when that principal holds none | every caller acts as the entrypoint's unauthenticated identity (the entrypoint mints it a real identity, so trust-mode agents still accept the delegations) and is authorized against that principal's scopes |
| Authentication only | `enableAuth: true`, no authorization service | unfiltered | any authenticated user can call every tool |
| Authentication + RBAC | `enableAuth: true` + the entrypoint's authorization service (role/user files) | **filtered** to the caller's invoke scopes | denied without the scope |

**Authorization-only is what a platform-deployed entrypoint gets** when an operator turns `enableAuth` off on a cluster running RBAC: the platform stamps the authorization service regardless of the authentication switch. So an `enableAuth: false` entrypoint whose principal holds no grants answers `tools/list` with an empty catalog — that is the expected result, not a broken deployment. Scope its reach with `runAs`.

**Who the unauthenticated caller is** (`enableAuth: false`, or any `transport: stdio` call — stdio has no HTTP surface for a token to arrive on, so `enableAuth` is inert there): `defaultUserIdentity` when set, otherwise the `runAs` system user — and an empty `runAs` means `system:default`, not a dev principal. Precedence matches the event-mesh entrypoint: the static identity is an identity source and wins; `runAs` is the terminal no-identity fallback. Under enforced RBAC that ordering decides whether the entrypoint reaches anything — `system:default` holds `agent:*:invoke`/`workflow:*:invoke`, while a plain `defaultUserIdentity` holds only what the catalog grants it (normally nothing, so the entrypoint reaches no agents). So: leave `defaultUserIdentity` empty unless you specifically want calls attributed to a named person, and point `runAs` at a scoped system user to narrow reach. `defaultUserIdentity` must not be `system:`-prefixed — rejected at startup and at create/update, because it would take that system user's scopes while bypassing `runAs`.

Both authenticated modes use the same OAuth setup below — RBAC just adds the authorization service on top. RBAC scope shape: one invoke scope per target — `agent:<dashed-uuid>:invoke` for a platform-deployed agent, `workflow:<dashed-uuid>:invoke` for a deployed workflow, `agent:<name>:invoke` only for a YAML-authored or built-in agent (wildcards `agent:*:invoke` and `workflow:*:invoke`; the agent wildcard does not cover workflows). Under RBAC a missing tool in the client's list is a **scopes problem, not a connection problem** — check the user's roles before debugging transport. Role/user administration depth → `sam-operate`.

## Securing with OAuth (UC-23 — e.g. Keycloak)

What the entrypoint implements: OAuth 2.1 authorization-code + **PKCE (required)**, **dynamic client registration** (RFC 7591) so MCP clients self-register, and the discovery metadata clients need (RFC 9728 protected-resource + RFC 8414 authorization-server documents, served at the proxy's `/.well-known/...` paths for the entrypoint). Clients discover all of it from the 401 challenge — no client-side endpoint hand-configuration.

**IdP-side (Keycloak or any OIDC provider):**
- The upstream IdP client lives in the **cluster-scoped provider catalog**, and the entry used is chosen by the platform's `EXTERNAL_AUTH_PROVIDER` environment variable (default `azure`) — **shared across MCP entrypoints, not one client per entrypoint, and not an entrypoint field** — so configuring it is an `sam-operate` task.
- **Which redirect URI to allowlist depends on the callback mode** (`stateRedirectionEnabled`, default on — see Agent Mesh-side):
  - **Default (state redirection on):** allowlist **one** dispatcher URI for *all* MCP entrypoints — `<webui-base>/api/v1/auth/callback`. The IdP returns to that dispatcher, which verifies the signed state and forwards to each entrypoint's `/oauth/finish`.
  - **Legacy (state redirection off):** allowlist this entrypoint's **own** `<external-base>/gw/<slug>/oauth/callback` (one per entrypoint). Turn the mode off only for a self-managed IdP that allowlists each entrypoint's callback. The slug is immutable, so this entry survives delete+recreate **if you reuse the slug**.
- Scopes: `openid`, `email`, `profile`, `offline_access` (refresh).

**Agent Mesh-side (names only — full YAML via `sam-declarative-config`):** `enableAuth: true`. There is no field naming the IdP: the platform fills in the provider from its cluster-wide `EXTERNAL_AUTH_PROVIDER` environment variable (default `azure`), which names a **cluster-scoped IdP provider catalog entry**; the issuer, client id, and client secret live in that shared provider config (a `${VAR}` env reference for the secret, never a literal), so standing one up is an `sam-operate` task, not an entrypoint field. (The entrypoint's own `issuer` — advertised in its `/.well-known` metadata, unrelated to the IdP — is **not** the bare external base: it is `<external-base>/gw/<slug>`, per entrypoint, with the external base baked in from `WEBUI_FRONTEND_SERVER_URL` at config-build time. With no slug it is `<external-base>/gw/<uuid>`, one more reason to set a slug before handing the endpoint to clients or an IdP. Locally, where that env var is unset, no issuer is emitted and the runtime falls back to `MCP_EXTERNAL_BASE_URL`, then a `host:port` that does not match the entrypoint's real URL — so for local OAuth, set `MCP_EXTERNAL_BASE_URL` to the entrypoint's external URL.) `allowedRedirectUris` — the allowlist of *MCP-client* redirect URIs (loopback hosts match any port per RFC 8252; leaving it empty logs a security warning); and `userIdClaim` (`email` default; `sub`/`upn`/`preferred_username` options). Two fields pick the callback mode: **`stateRedirectionEnabled`** (default `true`, recommended) routes the IdP callback through the shared dispatcher; **`oauthDispatcherUrl`** is the dispatcher's callback URL and **auto-derives from the cluster WebUI base (`WEBUI_FRONTEND_SERVER_URL`) → `<webui-base>/api/v1/auth/callback`** — set it only to target a non-WebUI dispatcher. State redirection has **three** outcomes, not one fallback:
- **Left unset (the usual case).** The platform derives the dispatcher URL from `oauthDispatcherUrl`, else `<WEBUI_FRONTEND_SERVER_URL>/api/v1/auth/callback`, and turns state redirection on **if and only if** one is derivable. If neither is, it silently uses the legacy per-entrypoint callback. Nothing announces which you got — check the YAML preview for `oauth_dispatcher_url`.
- **Explicitly `true` with nothing derivable, on an auth-enabled entrypoint.** A hard **422 at create/update**, naming all three remedies (set `oauthDispatcherUrl`, configure `WEBUI_FRONTEND_SERVER_URL`, or set the field `false`). It fails closed deliberately — the alternative is advertising a callback the IdP never registered and debugging an opaque `redirect_uri` error at login.
- **Created while a base URL existed, deployed after it disappeared.** Falls back to the legacy callback with a WARN (`mcp gateway state redirection requested but no dispatcher URL available; using legacy callback`) — the only path where degradation rather than rejection is the behaviour.

In hand-written runtime YAML the pairing is a **startup error**, not a fallback: `state_redirection_enabled: true` requires both `oauth_dispatcher_url` and `enable_auth: true`.

**What breaks when you turn auth on (answer this before the user asks):**
- Every existing client gets 401 until its user completes the OAuth flow. No grace period.
- The entrypoint mints its own short-lived JWTs (≈1 h; 2 h max). On a standalone gateway deployment each MCP entrypoint signs with its own **per-entrypoint key**. That key **survives restarts**: it is derived from the deployment signing seed when one is set (the `session_secret_key` app config, or the `SESSION_SECRET_KEY` env var), and otherwise generated once and persisted to disk — `$SAM_DATA_DIR/keys`, or `./keys` relative to the working directory when `SAM_DATA_DIR` is unset. Outstanding tokens are invalidated only when that key file's directory isn't durable — a replaced container with no volume, a read-only filesystem, or an I/O error writing the key. Either way, clients holding an IdP refresh token re-authenticate silently; others see a login prompt (in Claude Code: re-run `/mcp` and log in). Expected behavior, not a bug.
- On a standalone gateway deployment, tokens from one entrypoint don't work at another (per-entrypoint keys — intentional blast-radius limit).
- With RBAC on, under-scoped users see a *shorter tool list*, not an error — expect "where did my agent go" questions.

## Verify

`claude mcp add … && /mcp` → tool list shows `<prefix>_<skill>` entries, the prefix being `<kind>_<uuid-tail>` for a platform-deployed agent and the plain name for a built-in, with each agent's display name carried in the tool's title and description → call one. 401 loop = the MCP-client redirect URI missing from `allowedRedirectUris`, **or** the IdP client's allowlist missing the callback for your mode (the dispatcher `<webui-base>/api/v1/auth/callback` when state redirection is on, the per-entrypoint `/gw/<slug>/oauth/callback` when off); empty tool list under RBAC = missing invoke scopes — `agent:<dashed-uuid>:invoke` for a platform-deployed agent (`agent:<name>:invoke` for a built-in or YAML-authored one), `workflow:<dashed-uuid>:invoke` for a workflow-backed tool, which `agent:*:invoke` does not cover.
