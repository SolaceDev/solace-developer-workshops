# Connector type catalog (9 types / 16 subtypes)

Field names below are for **naming and recognition** — they are real keys from the live catalog, safe to mention to the user. Full YAML shape, nesting, and validation: `sam-declarative-config` (or create one connector in the builder UI and `sam config pull` it). The builder UI form is generated from the same schema, so the UI is always current. When the user needs an exact **tool name** (e.g. for agent instructions), the wizard's Select Tools step shows it — don't guess tool names this file doesn't state.

## Availability

`document_db`, `graph_db` and `search` are still experimental. Every type has its own page in the Connectors section of the Agent Mesh docs.

## `sql` — postgres · mysql · mariadb · mssql · oracle

Agent gets a SQL query tool: the agent's LLM writes the SQL and the tool executes it against your database. The tool introspects the schema on startup and samples up to 100 rows per table into the tool description so the LLM knows the shape. **This is not tunable from a connector** — the connector emitter hard-codes the tool's config, so `auto_detect_schema` / `schema_summary_override` / `schema_sample_size` set as connector values are silently ignored. Those keys are real, but only on a hand-authored `execute_sql_query` built-in tool entry, which is a different (non-connector) authoring path. Fields: `hostname`, `port` (defaults 5432 / 3306 / 3306 / 1433 / 1521), `database`, `username`, `password`. Oracle uses `service_name` instead of `database`. MSSQL adds `encrypt` (yes / no / strict) and `trust_server_certificate`. **The tool can run any SQL the credentials allow — use a read-only DB user scoped to the needed schemas** (the UI shows this warning; repeat it).

## `knowledge_base` — bedrock

RAG retrieval from an Amazon Bedrock Knowledge Base. Fields: `kb_id`, `region`, then `auth_type`: `access_key` (`aws_access_key_id` + `aws_secret_access_key`) or `iam` role chaining (`aws_account_id` + `role_name`, optional `session_name`, optional `external_id` for cross-account). IAM permissions: `bedrock:Retrieve` and `bedrock:GetKnowledgeBase` on the KB.

## `api` — openapi

Every operation in an OpenAPI 3.x spec becomes an agent tool (operations without an `operationId` still appear, with a generated name). Spec via `specification_url` **or** file upload; `base_url` is required and overrides the spec's `servers`. Before authoring (UI or declarative), collect: the spec source, the `base_url`, and the auth scheme + where the credential goes (header/query and its name) — the user's message rarely contains all three. Options: `custom_headers`, `allow_list` (comma-separated operation IDs). `auth_type`: `none` | `apikey` (header or query: `auth_apikey_location`, `auth_apikey_name`, `auth_apikey_value`) | `http` (basic or bearer) | `oauth` (authorization/token URLs, client id/secret, scopes). The UI can auto-detect the auth scheme from the spec.

⚠️ **A file embed reaches this target as text, not bytes.** The calling side resolves *early* embeds only; `artifact_content` is a **late** embed, so it is passed through untouched and each tool resolves it during its own execution. A plain REST endpoint cannot, so it receives the literal embed string. **Use a tool that resolves the embed** — there is no way today to get artifact bytes into an `api` connector call. In particular, do not reach for a `multipart/form-data` binary parameter: the connector's artifact-resolution path for multipart fields exists in the code but is not wired to anything, so an `artifact://` value fails the call outright with *"artifact URI … provided but no artifact service available"*.

⚠️ **A spec that never arrived still deploys.** With neither an uploaded spec nor an external spec URL, the connector is built with an unresolvable spec reference. It does not fail the deploy: the agent starts and **registers no tools from this connector at all**, so the model never sees them and there is no failing call to trace. The signals are two error log lines — one when the connector's config is built, one when the agent starts and finds no spec to load — plus a failed registration status carried back against the connector, so the connector's own card is the fastest place to see it. After creating or updating an `api` connector, confirm its tools actually appear rather than assuming a clean deploy means the spec landed. (Binding such a connector to a workflow `tool` node is the one loud case — that fails the deploy outright.)

## `mcp` — remote

Exposes a **remote** MCP server's tools to the agent — SSE or streamable HTTP only (`server_url`, `connection_type`); **there is no stdio/command subtype**. If the user's MCP server only runs locally via stdio, that is not a connector. `auth_type`: `none` | `apikey` | `http` | `oauth` (`auth_oauth_mode`: `discovery` or `manual`). Tool selection: at most one of `tool_name` (exactly one tool) / `allow_list` / `deny_list` — colliding gives *"tool_name, allow_list, and deny_list are mutually exclusive — got …"*. A `manifest` may not be combined with any of those three, because the manifest **is** the registered tool set: *"manifest is mutually exclusive with `<field>` — the manifest already declares the tool set"*. **`selected_tools` is the exception and works the opposite way — it *requires* a manifest** (*"selected_tools cannot be used without a manifest…"*), its names must appear in that manifest, and an empty string is rejected; omit the key to select all. `tool_name_prefix` is orthogonal to all of this. Also available: `hil` (per-tool human-in-the-loop approval gating).

**OAuth MCP servers need a `manifest`.** By default the agent discovers tools by calling the server's `tools/list` when it starts. Delegated OAuth blocks that call (401 until a user signs in), and **no user is present at agent startup** — so without a manifest the agent boots with **zero tools**. Which auth types this actually applies to:
- `connection_type: streamable-http` (the default) + `auth_type: oauth` → **hard requirement**: the runtime refuses to register the client without a manifest (*"streamable-http server with auth requires a manifest; tools/list is blocked until the user completes OAuth — either provide manifest/manifest_file or switch to an SSE transport"*).
- `connection_type: sse` + `auth_type: oauth` → the runtime does **not** block it; the fail-fast guard is streamable-http only, and its own error text offers SSE as the alternative to a manifest. Startup discovery still 401s, so a manifest remains the safer choice if tools come up empty.
- `auth_type: apikey` or `http` → **no manifest needed.** Those credentials are emitted as static request headers (or a URL query param), so they ride on the startup `tools/list` and discovery succeeds with no user present. Don't prescribe a manifest here — it would force you to drop `allow_list`/`deny_list`/`tool_name` for nothing.
- **`sam config apply` / deploy SUCCEEDS either way** — the connector saves, the agent deploys "successfully," and only at *runtime* does the connector show **0 tools**. Deploy-success ≠ working tools; verify the tool count.

So for an MCP connector with `auth_type: oauth`, supply an inline `manifest`: a list of entries, each with `name`, `description`, an optional `inputSchema`, and an optional `outputSchema`. The `outputSchema` is honoured by the runtime: its top-level `properties` name the fields a workflow addresses as `{{node.output.mcp_structured_content.<field>}}`, and a reference they do not name is reported as unverified when the workflow starts. Supply it whenever the server publishes one — on this path there is no live `tools/list` to discover it from. Get the tool list by running the builder's Select-Tools / discovery step **after** entering credentials, or from the server's published tool list, then carry those entries as the `manifest`. With a manifest the agent advertises the tools at startup and the per-user OAuth flow runs on first tool call. The manifest also lets you pin/restrict exactly which tools register. Full YAML shape: `sam-declarative-config`.

**Adding a `manifest` to an existing connector — the atomic-PATCH trap.** `sam config apply` sends the connector's `name` + `description` + `values` (the manifest is inside `values`) as **one** `PATCH /api/v1/platform/connectors/{id}`. The server validates the whole body; a failure on *any* field returns a 4xx and **nothing in `values` persists** — for an `mcp` connector `updatedAt` never advances and the agent stays at 0 tools. (The one type where `updatedAt` can move on a failed apply is `api`/`openapi`: its `specification_file` goes up in a separate `PUT .../{id}/resource` before the PATCH and stays persisted regardless.) The classic misdiagnosis is "the reconcile diff ignores the manifest" — it does **not**; `sam config plan` correctly shows the `~ <connector> update`. What actually happened is a sibling field was rejected. Two common culprits. First, **tool-selection exclusivity**: adding a `manifest` to a connector that already has `allow_list`, `deny_list`, or `tool_name` is rejected outright — remove those when you add the manifest. Second, **length**, enforced on update in both directions identically to create: `name` 3–255 and `description` 10–1000. A description that quietly grew to 1001 chars fails with 422 *"description must be at most 1000 characters"*, and one trimmed to 9 chars fails with *"description must be at least 10 characters"* — either takes the bundled manifest down with it. (An omitted or empty field means "preserve", so only a non-empty too-short value trips the minimum.) Diagnosis order when a manifest "doesn't take": (1) strip any `allow_list`/`deny_list`/`tool_name` from the same connector; (2) confirm `apply` actually reached the server — a wrong `--url`/port yields connection-refused that hides the real 422; (3) read the apply output for a 4xx on a sibling field (description/name length — note `safetext`/`safename` validation runs on *create* only, not update); (4) fix that field and re-apply — the manifest then persists and `updatedAt` moves. Verify with the runtime tool count, not deploy success.

**Discriminator:** user already runs an MCP server the agent should consume → this type. User wants to *expose* Agent Mesh agents to MCP clients → MCP entrypoint (`sam-entrypoints`). One-agent inline MCP wiring exists in runtime YAML, but the connector is the taught path.

## `slack` — bot

Outbound posting: a send-message tool and an update-message tool (text/Markdown, threads, attachments, Block Kit). **The channel is a tool-call parameter, not connector config** — the agent supplies a channel ID, `#channel-name`, user ID, or user email per call; tell the agent its target channel in its instructions. Single config field: `slack_bot_token` (a bot token, `xoxb-…`; the schema recommends `chat:write`, `files:write`, `users:read`, `users:read.email`; invite the bot to the channel, or grant `chat:write.public` to post to public channels without joining). **Inbound** — people chatting with agents from Slack — is the Slack *entrypoint*. Machine-triggered notifications → this connector.

## `event_mesh` — solace

The agent sends requests to backend services over a Solace broker. The broker connection is **required and custom** — all four of `broker_url`, `broker_vpn`, `broker_username`, `broker_password` (credentials are never inherited from the Agent Mesh broker). Unique among connectors: **you define the tools** — an `operations` array where each operation becomes one agent tool with `tool_name` + `tool_description` (what the LLM sees), a `topic` template with `{property_name}` placeholders (legacy `{{ param }}` still parses), `payload_format` (json/yaml/text), request/reply (`wait_for_response: true`, `request_expiry_ms`) or fire-and-forget, and an `input_schema` (JSON Schema) parameter declaration. Inbound (a mesh topic triggering an agent) → eventmesh entrypoint.

## `document_db` — mongodb · dynamodb *(experimental)*

MongoDB: `scheme` (`mongodb` / `mongodb+srv`), `hostname`, `port` (default 27017; ignored for `mongodb+srv`), `username`, `password`, optional `database`, required `collection`, optional `options`. DynamoDB: `region`, `table_name`, `auth_type` `access_key` or `iam` (`role_arn`, optional `session_name` / `external_id`). This — not a third-party MCP server — is the product path for "let the agent look up records in Mongo/DynamoDB".

## `graph_db` — neo4j · neptune *(experimental)*

Neo4j: `scheme` (`neo4j` / `neo4j+s` / `bolt` / `bolt+s`), `hostname`, `port`, `username`, `password`, optional `database`. Neptune: `scheme`, `hostname`, `port`, `region`, AWS `auth_type` access_key or iam (`role_arn`).

## `search` — elasticsearch · opensearch *(experimental)*

Elasticsearch: `scheme`, `hostname`, `port` (or Elastic Cloud `cloud_id`), plus `api_key` (or `username` / `password`). OpenSearch (managed domain or Serverless): `scheme`, `hostname`, `port`, `region`, AWS `auth_type` access_key or iam. **Subtype ≠ vendor:** the `opensearch` subtype is specifically AWS-managed OpenSearch (domain/Serverless, AWS-auth); a **self-hosted** OpenSearch cluster speaks the Elasticsearch-compatible API, so use the `elasticsearch` subtype for it.
